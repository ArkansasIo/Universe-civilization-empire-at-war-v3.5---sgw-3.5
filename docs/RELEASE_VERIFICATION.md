# Release Verification Checklist

Use this checklist for every release candidate. A successful static-site deployment only establishes that the configured build and publish steps completed; it does not prove gameplay correctness, security, or type safety.

## Pull request checks

- [ ] Install dependencies from the committed lockfile using the selected package manager.
- [ ] Run TypeScript type-checking and resolve all blocking errors.
- [ ] Build the Vite client with the same Node.js major version as CI.
- [ ] Confirm `dist/index.html` exists and every generated asset reference resolves.
- [ ] Run unit tests for game rules and data migrations.
- [ ] Verify the UI mounts in a browser at desktop and mobile viewport sizes.
- [ ] Inspect browser console output for runtime exceptions and failed chunk loads.

## Game-rule regression cases

### Resources and transactions
- [ ] Reject negative, NaN, infinite, or over-cap resource amounts.
- [ ] Reject a purchase when the player cannot afford the complete cost.
- [ ] Ensure a failed purchase does not partially deduct resources.
- [ ] Ensure a retried command cannot deduct or grant resources twice.

### Turns and production
- [ ] Process a single eligible turn exactly once.
- [ ] Handle delayed schedulers and duplicate worker execution safely.
- [ ] Enforce the configured turn-storage cap.
- [ ] Verify production, upkeep, and income calculation order is deterministic.

### Combat and fleets
- [ ] Reject attacks against invalid targets and unavailable fleets.
- [ ] Verify resource and unit deductions occur atomically with accepted orders.
- [ ] Confirm combat results are generated by trusted server logic for competitive play.
- [ ] Confirm losses, survivors, and debris remain internally consistent.

### Authentication and authorization
- [ ] Unauthenticated clients cannot access private player data.
- [ ] One player cannot read or modify another player's profile, resources, or colonies.
- [ ] Ordinary players cannot grant themselves admin status or change system configuration.
- [ ] Market sellers cannot spoof another player's identity.
- [ ] Firestore rules tests pass against the Firebase Emulator Suite.

## Deployment and rollback

- [ ] Confirm the expected branch and commit SHA triggered the deployment.
- [ ] Confirm the build artifact uploaded successfully.
- [ ] Confirm the Pages deployment URL loads the current application.
- [ ] Keep the previous working commit available for a quick rollback.
- [ ] Document any temporarily non-blocking checks, including known TypeScript errors.

## Evidence to record

For each release, record the commit SHA, CI run URL, test outcomes, deployment URL, and known issues. Do not label a release fully verified when checks were skipped or configured as non-blocking.
