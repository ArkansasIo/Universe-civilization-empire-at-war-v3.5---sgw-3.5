# Universe Streaming Architecture

The universe is generated by address rather than materialized globally. A chunk is identified by `(galaxy, x, y, z)` and its content is derived from the universe seed plus generator version and coordinates.

## Runtime pipeline

```text
player/camera position
        |
        v
worldToChunk()
        |
        v
load-radius query
        |
        +--> deterministic chunk seed
        |          |
        |          v
        |     chunk generation
        |
        +--> memory cache / LRU eviction
        |
        +--> persistent ChunkStore
        |
        +--> faction exploration / fog of war
        v
render + simulation
```

## Determinism

Never use global RNG state for streaming. Loading chunk `(5,0,0)` before `(0,0,0)` must produce exactly the same data as loading them in the opposite order. `deriveChunkSeed()` is the authoritative seed boundary.

## Coordinates

- Chunk size defaults to 400 world units.
- A sector contains 8×8×8 chunks by default.
- Streaming uses a cubic Chebyshev radius, which is predictable for a 3D galaxy renderer.
- `galaxyChunkRadius` can enforce a hard boundary.

## Persistence

`ChunkStore<T>` is deliberately storage-agnostic. The current `MemoryChunkStore` is suitable for tests and local development. A production implementation can map the same interface to MySQL, PostgreSQL, Redis, a document store, or an MMO shard service.

Only persistent gameplay mutations need to be stored. Purely procedural data can be regenerated from the seed and generator version.

## Fog of war

`ExplorationState` is faction-scoped. Discovering a chunk for Tau'ri does not reveal it to another faction. Exploration state is gameplay state and therefore must not be included in the deterministic chunk seed.

## Server authority

Clients may request a chunk by coordinate, but the authoritative server owns:

- generator version
- universe seed
- chunk bounds
- faction ownership
- discovered/explored state
- modified system state
- jump/stargate permissions

A client-provided chunk payload must never overwrite authoritative state.

## Scaling

With a load radius of 2, the active cubic region is 5³ = 125 chunks. Memory usage is therefore proportional to active players and their requested map regions instead of total universe size.

For a large MMO, shard ownership can be layered above `ChunkCoord`: hash the coordinate into a stable shard ID, then route chunk requests to the owning simulation process.
